- 이 구간의 최대 동시 실행 수는 3이라 동시 4 이상 값은 재현하지 못했다.

- 시뮬레이터 카드는 후속 질문을 하도록 짜여 있어 answer 가 최소 3회다. 실제 사용자는 이보다 적을 수 있다.

**계산 방식은 두 가지다.**

(가) **한계 비용** — 서버가 꽉 차게 일할 때 세션 하나의 몫이다. 시간당 1,943원(gov)을 시간당 세션 수로 나눈다.

시간당 세션 = 부하 단계 3분 동안 처리한 answer 수 × (3,600 ÷ 단계 시간) ÷ 4(세션당 answer 횟수) [실측 기반]. 같은 시간에 intake·search·doccheck·rewrite 도 함께 처리했고 그 몫은 빼지 않았으므로 보수적인 값이다. intake 로 셈하면(÷ 1.62) 더 크게 나온다(172 · 264 · 398 · 474).

| 동시 처리 | answer/시간 | 시간당 세션 | 세션당 비용(1,943원/h) | 품질 |
|---|---|---|---|---|
| 1 | 556 | 약 139 | 약 14.0원 | answer p95 8.4s, 발췌 3.6% |
| **2 (권장 운영점)** | 798 | **약 200** | **약 9.7원** | answer p95 11.3s, 발췌 4.9% |
| 4 | 1,115 | 약 279 | 약 7.0원 | p95 16.5s, 발췌 14.0%, 1,500자 rewrite 504 |
| 8 | 1,520 | 약 380 | 약 5.1원 | p95 17.8s, **발췌 50.5%** |

- 이전 시나리오 A(98 세션, 20원)·B(250, 7.8원)·C(600, 3.2원)는 가정이었다. 실측은 A 보다 낫고 B 근처는 품질을 잃어야 닿으며, C 는 생성 속도 포화(약 54 tok/s)로 닿지 않는다.

(나) **실제 비용** — 서버는 사용량과 상관없이 켜 둬야 하므로 월 고정비를 월 세션 수로 나눈다.

| 1,000 | 약 1,399원 |

### 3-4. 용량 추정

- L4 1장이 품질을 지키며 처리하는 세션은 **시간당 약 200**(동시 2) 이다 [실측 기반, §3-3]. 품질을 버리면 약 380(동시 8, 답의 절반이 발췌)까지 오른다.
- **실제 한계는 처리량보다 12초 답변 예산이었다** [실측]. 동시 4부터 answer 가 예산을 다 써서 발췌로 바뀌는 비율이 14%, 동시 8 에서 50.5%가 됐다. 오류(5xx)는 1,500자 rewrite 504 뿐이었다. 즉 부하는 오류가 아니라 **품질 저하**로 먼저 나타난다.
- 생성 속도는 동시 4부터 단계 평균 약 54 tok/s 에서 포화한다. vLLM 대기열은 최대 1~2라 줄 서기보다 생성 속도가 병목이다.
- **운영 권장: 동시 처리 2건 이하** [실측 기반]. 근거는 위 두 줄이다. 동시 2 까지는 answer p95 11.3초·발췌 4.9%로 목표(p95 ≤ 13초, 발췌 증가 ≤ +15%p)를 지켰고, 동시 4 에서 p95 16.5초로 목표를 넘었다. 지금 코드는 answer·intake 와 GPU 엔드포인트의 동시 처리를 막지 않으므로(rewrite 만 상한), 이 권장은 운영으로 지킨다(시연은 한 사람이 쓰므로 동시 1~2). 코드로 지키려면 answer·intake 에 전역 세마포어(넘치면 429·대기 안내)와 vLLM `--max-num-seqs` 명시가 필요하다(마감 뒤, `architecture.md` 「알려진 한계」).
- 그 밖의 상한도 있다.
  - rewrite 동시 2건, 접속 주소당 1건(터널 뒤에서는 전역 1건) [코드]
  - GPU 서버 vCPU 4개
  - KV 캐시 48,192 토큰, 8,192 토큰 요청 기준 최대 동시 약 5.88 [실측, `vllm:cache_config_info`]. 동시 8 에서 사용률 최대 0.60. 이전 추정(동시 약 20건)은 틀렸다.
  - GPU 메모리: 부하 중 여유 최소 2,558 MiB(사용 최대 20,476 / 23,034 MiB) [실측].
- 용량을 늘리는 가장 싼 방법은 GPU 서버가 포기한 요청을 vLLM 에서도 끊는 것(§2-1 카운터 관찰)과 검증 LLM 호출 줄이기(§4 #2)다. 둘 다 효과 크기는 재지 않았다.

## 6. 발표에서 쓸 수 있는 문장 / 쓰면 안 되는 문장

### 쓸 수 있는 문장
- "진단 결과는 규칙 엔진이 0.005초 만에 냅니다. GPU 가 멈춰도 체크박스 진단은 그대로 동작합니다."
- "카드 질문 답변은 평가셋 45문 기준 중앙값 약 3초, 95%가 약 11.6초 안에 끝났습니다(배포 앱 경로 30건 p95 10.3초)." — 합성 질문 5회 반복 측정의 중앙값 5.7초(`EVIDENCE.md`)와 섞어 말하지 않는다.
- "답변에는 12초 예산이 있습니다. 시간 안에 검증을 통과하지 못하면 지어내는 대신 근거 원문을 그대로 보여 줍니다."
- "검색은 약 1초이고, 정답 조항이 상위 5개 안에 들어오는 비율은 96%입니다(55문)."
- "LLM 은 공공기관 클라우드 안의 GPU 1장에서 돕니다. 사용자 서술은 외부 AI 서비스로 나가지 않습니다."
- "공개 정가로 셈하면 지금 구성은 월 약 140만 원(VAT 별도)입니다. 그중 83%가 GPU 서버입니다. 해커톤 기간 비용은 주최 측이 부담했습니다."
- "부하를 걸어 보니 GPU 1장으로 품질을 지키면서 시간당 약 200 세션을 처리했습니다. 꽉 찰 때 세션당 약 10원입니다." — '동시 사용자 N명' 이 아니라 '시간당 세션'으로 말한다.
- "부하가 늘면 오류가 아니라 근거 원문 발췌가 늘어납니다. 동시 8건에서도 오류는 긴 문서 바꾸기 504 몇 건뿐이었습니다."
- "세션 하나는 실제 토큰 약 2.2만 개를 씁니다(대부분 근거 조문 입력)."
- "GPU 1장으로는 동시에 처리하는 요청을 2건 이하로 두는 것을 권합니다. 4건부터는 오류가 아니라 근거 원문 발췌가 늘어납니다."

### 쓰면 안 되는 문장 (근거가 없거나 틀리다)
- "동시 사용자 N명을 지원합니다" — 잰 것은 동시에 처리 중인 요청 수(대기 시간 없음)와 시간당 세션이다. 사람 수로 바꾸려면 생각 시간 가정이 필요하다.
- "모든 답변이 12초 안에 나옵니다" — 12.67초, 시뮬레이터 15.03초 사례가 있다.
- "세션당 비용은 X원입니다" (단정) — 꽉 찰 때 약 10원(동시 2)이고, 사용량이 적으면 140~1,400원 이상이다. 말하려면 가정을 함께 말한다.
- "48 tok/s" — 출처가 확인되지 않았다. 실측은 단일 요청 p50 35.7, p90 45.8 tok/s 다.
- "실제 운영비는 월 140만 원입니다" — 정가 추정이다. 실제 청구액은 미확인이다.
- "외부 API 보다 싸다" — 토큰 단가만 보면 외부 API 가 더 싸다. 자체 GPU 를 택한 이유는 비용이 아니라 개인정보다.
- "휴대폰 데이터망에서도 5초 안에 열립니다" — 느린 망에서 잰 적이 없다.
