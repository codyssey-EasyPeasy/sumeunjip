## 2. 내부 LLM (vLLM) 실행 명령

실제로 떠 있던 프로세스의 명령줄입니다(`/proc/<pid>/cmdline`). `gpu/llm_start.sh` 가 만드는 명령과 같습니다.

```
~/vllm-venv/bin/python3 ~/vllm-venv/bin/vllm serve ~/models/Qwen3-8B-AWQ \
  --host 127.0.0.1 --port 8001 --served-model-name qwen3-8b \
  --max-model-len 8192 --gpu-memory-utilization 0.6 \
  --no-enable-log-requests --no-enable-log-outputs --disable-uvicorn-access-log
```

환경 변수(`gpu/llm_start.sh`, 실측은 `docs/evidence/infra-2026-10-31-night.md`): `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `VLLM_NO_USAGE_STATS=1`, `DO_NOT_TRACK=1`.
추론 API 쪽(`gpu/start.sh`)은 `HF_HOME=$MODELS_DIR`(서버 값 `~/models`), `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1` 입니다.

## 6. vLLM 처리량 요약 (회수 로그 집계)

- 원자료: vLLM 이 10초마다 남기는 통계 줄(`loggers.py`) 400줄, 로그 시각 **2026-11-01 02:47:48 ~ 04:42:28**. vLLM 은 요청이 있을 때만 이 줄을 남깁니다. 그래서 400줄은 약 67분 분량의 활동 구간입니다.
- 이 구간에 어떤 요청이 들어왔는지는 로그에 없습니다(요청 로그 끔). 시연·점검 트래픽으로 추정하지만 미확인입니다. 부하 시험(`docs/COST_LATENCY.md` §3-3, 2026-10-31 23:37~23:52)과는 다른 구간입니다.
- 값은 10초 창의 평균입니다. 요청 하나의 속도가 아닙니다. 그래서 `docs/COST_LATENCY.md` 의 요청별 단일 생성 속도(p50 35.7 tok/s)와 직접 비교하지 않습니다.
- 집계: 로그 줄마다 `Running`(처리 중 요청 수)으로 묶고 `Avg generation throughput` 의 중앙값·90분위·최대를 셌습니다(python3, 이 문서 작성 때).

- 접두 캐시 적중률은 27.8~51.5% 였습니다.
- 동시 처리 수가 늘면 창당 생성 합계가 늘어납니다(1건 28.3 → 2건 50.0 → 3건 57.5 tok/s). 동시 3~4건에서 합계 약 115~120 tok/s 라는 `docs/COST_LATENCY.md` 의 값은 부하 시험 구간에서 잰 것이라 이 표로는 다시 확인되지 않습니다.

## 8. 다시 만들 때 남은 빈칸

| 빈칸 | 영향 | 대응 |
|---|---|---|
| vLLM 설치 명령 기록 없음 | 같은 의존성 조합이 깔린다는 보장이 없음 | 3-1 의 버전으로 고정 설치, 핵심 패키지 버전을 3-1 표와 대조 |
